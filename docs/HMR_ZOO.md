# HMR zoo: 同一段影片、同一組人框、多個 3D 人體模型並排比較

2026-11-22/23 建立（Allen 交代，pm 轉達）。目的：拿不同運動的影片，把我們用過的 3D 人體模型放在同一格式下並排比較，
讓 Allen 看影片、自己挑「某個運動最適合哪個模型」。**本文件不下「哪個最好」的結論**，只給數字、影片與已知問題。

全部是新增檔案，沒有改任何既有檔案（既有 detector、converter、README 都沒動）：

| 路徑 | 內容 |
|---|---|
| `preprocessors/track_person.py` | 人框偵測＋追蹤＋外觀再識別（ReID）模組，所有模型共用它產的框 |
| `detectors/wham_detector.py`、`nlf_detector.py`、`sam3db_detector.py`、`onlinehmr_detector.py` | 新增的四個 detector（類別 `XDetector.detect_video(video, bbox_file)`，也可當 CLI） |
| `hmr_zoo/` | 比較框架：`common.py`（共用常數與 npz 格式）、`models.py`（模型登錄）、`adapters.py`（既有 HybrIK/GVHMR/InstantHMR/RTMW3D 的轉接）、`run_model.py`、`compare.py`、`render.py`、`prep_clip.py`、`boxes.py`、`vram.py` |
| `scripts/hmr_zoo_prepare_clips.sh`、`hmr_zoo_make_tables.py`、`hmr_zoo_flowhmr_probe.py` | 準備本次的 12 個片段、彙整成表、FlowHMR 是否還能跑的探針 |
| `docs/RUNNING_hmr_zoo.md` | 每次開 GPU 與結束的紀錄 |
| `outputs/hmr_zoo/`（不進 git；`.gitignore` 還沒加，見「待辦」） | 片段、預測 `.npz`、`compare_2d.mp4`、`metrics.csv` |

## 怎麼用

一個「片段資料夾」（clip dir）是單位：`clip.mp4`、`boxes.json`、`meta.json`，各模型預測 `<model>.npz`，輸出 `compare_2d.mp4`、`metrics.csv`。

```bash
cd /home/allen/SkeletonHub
export CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=<空卡編號>   # 先跑 ~/hq/bin/gpufree

# 1. 做片段（剪 5–10 秒 + 追蹤 + 人框）。追蹤要 reidtrack 環境
/home/allen/miniconda3/envs/reidtrack/bin/python -m hmr_zoo.prep_clip \
    --video /path/to/video.mp4 --start 14.2 --dur 7 --sport roller_skating --name my_clip
#   FineFS stage 2 的片段（直接沿用 finefs_preproc 的框）：--finefs 3A_3A_0133 --sport figure_skating
#   畫面有多人、自動選錯人時：--point X,Y,FRAME（指定某幀上那個人身上的一個像素）

# 2. 依序跑所有模型並排比較（每個模型在自己的 conda 環境裡以子程序執行，模型只載入一次、跑完全部片段）
/home/allen/miniconda3/envs/reidtrack/bin/python -m hmr_zoo.compare \
    --clips outputs/hmr_zoo/roller_skating/my_clip --gpu <空卡編號> \
    [--models hybrik,gvhmr,wham,instanthmr,nlf,sam3db,onlinehmr,rtmpose3d] [--skip-existing]
#   結果：<clip>/compare_2d.mp4、<clip>/metrics.csv、各模型 <clip>/<model>.npz
#   只重畫影片和指標（不用 GPU）：加 --render-only

# 3. 彙整成 markdown 表
python scripts/hmr_zoo_make_tables.py
```

每個模型的預測存成同一種 `.npz`（沿用 finefs_preproc Stage 2 的格式）：`verts_cam`（相機座標網格，SMPL 6890 點或 MHR 18439 點）、
`joints3d_cam`（17 個 H36M 關節，公尺）、`joints2d`、`K_fullimg`（內參）、`faces`、`fps_infer`、`peak_vram_gb`、`mesh_type`（smpl／mhr／skeleton）。

`compare.py` 開跑前與每個模型之間會檢查那張卡有沒有別人的程序，有就停（共用機器規則）。

## 人框追蹤模組（`preprocessors/track_person.py`）

這是 `hmr_zoo` 的第 0 步，也可單獨使用：影片 → RF-DETR 偵測人 → BoT-SORT 追蹤（可加 OSNet 外觀 ReID）→ 挑主角那條軌跡
→ 修補斷頭與缺框 → 外擴 12% → 每幀一個框，輸出 `boxes.json` 與 `boxes_padded_112.txt`（每行 `x1 y1 x2 y2`，
即所有 SkeletonHub detector 的 `--bbox-file` 格式）。外擴 12% 是 finefs 的做法，免得手腳被切掉；`boxes.json` 另有未外擴的 `tight_clean` 與 `padded_125`。

```bash
/home/allen/miniconda3/envs/reidtrack/bin/python preprocessors/track_person.py \
    --input video.mp4 --out-dir outputs/track/video --tracker botsort-reid --device cuda
# --detector nano|small|medium|base   --tracker botsort|botsort-reid   --target auto|largest|point(--point X,Y,FRAME)
# --margin 1.12   --no-preview（預設會輸出 boxes_preview.mp4，把框畫在影片上，請用眼睛確認追到對的人）
```

- 流程、參數（`lost_track_buffer=150`、`high_conf=0.5`、ReID 融合 adaptive）與 reidtrack 專案相同；套件版本以那個環境為準（trackers 2.7.0、reid 0.1.0、rfdetr 1.12.1）。
  **`~/reid_tracking` 原專案沒有動**，只讀它的做法並呼叫它的 conda 環境 `reidtrack`；之後交接給周宜學請看它自己的 `HANDOFF.md`。
- 「挑主角」`auto` 是 finefs 的規則：整段上框面積乘畫面中心度最高的軌跡。單人場景通常對；畫面有多人時請看預覽影片，不對就改 `--point`。
- 不開 ReID（`--tracker botsort`）較快；reid_tracking 的筆記結論是單一主體不一定需要 ReID，離開畫面再回來或被遮住才有差。本次所有片段用的是開 ReID 的版本，沒有逐片段比較兩種的差別。
- 偵測結果會存成 `detections_<size>.npz` 快取，同一資料夾重跑不會重偵測。

## 指標怎麼算（同 finefs `stage2_eval_render.py`，沒有自己發明）

| 欄位 | 意義 |
|---|---|
| in-box % | 17 個關節投影到 2D 後落在共用框內的比例 |
| ctr err %h | 關節外接框中心與緊框中心的距離，占緊框高度的百分比（越小越貼人） |
| h ratio | 骨架投影高度除以緊框高度的中位數 |
| jitter | 根節點相對關節的二階差分，乘 fps 的平方，數字越大越抖（單位是公尺／秒平方，但各模型尺度不同，只適合同一個片段內比） |
| boneCV % | 8 根四肢骨長的「標準差÷平均」，越大代表骨長每幀變動越大 |
| yaw p95 | 骨盆朝向每幀變化的第 95 百分位（度）。高速旋轉的動作本來就大，不一定是壞事 |
| z-jump m | 骨盆深度每幀變化的第 95 百分位 |
| fps、VRAM | 只算推論（不含載入模型與讀影片），先丟掉第一個片段的暖機結果再計時；VRAM 是該程序在 `nvidia-smi` 看到的峰值 |

**這些全都不需要真值，只衡量「自己前後幀是否一致」和「投影與人框貼不貼」，不是 3D 準確度。** 沒有任何一個片段有 3D 真值（finefs 當初也沒有）。

## 驗收（我自己做的）

1. **和 11-15 的 finefs 數字對得上。** 同一個片段（`3A_3A_0133`、`4Lz_4Lz_0018`）、同一組框、同七個模型，用新框架重跑後與 `finefs_preproc/outputs/stage2/summary_with_onlinehmr.csv` 比：
   七項品質指標的最大差距是 in-box 0.05 個百分點、中心誤差 0.01、高度比 0.001、抖動 0.39、骨長變異 0.72 個百分點（SAM 3D Body 在 4Lz 上，其他 ≤0.03）、骨盆轉向 p95 2.8 度、深度跳動 0.007 公尺。
   GPU 本身有不確定性，SAM 3D Body 的差距就來自這裡。推論 fps 不同，因為 finefs 當時是同一張卡上和別的批次排在一起計時、沒做暖機，這次是獨占一張卡並暖機後的數字。
2. **新追蹤模組產的框和 finefs stage 2 的框幾乎一樣。** 在 `3A_3A_0133` 上，從原始 `clip.mp4` 重跑 `preprocessors/track_person.py`（偵測加 BoT-SORT 加 ReID，自動選主角），
   125 幀的緊框與外擴框中心平均相差 0.03 像素（最大 0.05），高度比 1.000，IoU 平均 1.000（最小 0.999）。只驗了這一支片段。
3. 每支新片段的 `boxes_preview.mp4` 都用眼睛看過（抽幀），確認追到的是主角。沒有逐幀看。
4. 七個網格模型與 RTMW3D 的 2D 疊圖在 `3A_3A_0133` 與 `v25_S_14s` 抽幀目視過，疊合位置合理。

沒驗：
- 其他 10 支新片段上，各模型數字沒有外部對照（沒有真值，也沒有別的實作可比）。
- RTMW3D 的 3D 座標單位與座標系（我用模型輸出的 `keypoints`，當作相機軸向的相對座標），只看了 2D 疊圖；3D 欄位不可信。
- 追蹤「開 ReID 與不開」在這些片段上的差別沒比。
- 同一片段重跑兩次的隨機性（只有 SAM 3D Body 看得到差異）沒有系統性量。
- 模型授權欄是備忘，沒逐條對照上游條款。

## 指標上各自的強弱（只描述數字，不是「哪個最好」）

下面是看過上面各表後，數字上很明顯的現象。是否足以挑模型，由 Allen 看影片判斷。

- **時間穩定度（jitter、boneCV）**：GVHMR 與 WHAM 這兩個時序模型的抖動通常最低（例如田徑平均 6.6、8.6，HybrIK 29.6、NLF 27.2）；HybrIK、NLF、SAM 3D Body 這三個逐幀模型抖動偏高。
  InstantHMR、OnlineHMR 因為是因果逐幀並加了濾波，抖動居中，但 InstantHMR 的骨長變異偏大（花式滑冰 9.6）。
  跳水是例外：OnlineHMR 的抖動最低（41），但骨長變異 31.8 偏高；GVHMR、WHAM 約 59。
- **貼人程度（ctr err、in-box）**：SAM 3D Body 與 RTMW3D 在花式滑冰、輪滑、田徑、棒球的中心誤差最小（田徑 2.6、棒球 2.2–2.9；跳水與拳擊替代片不是）；拳擊替代片上多數模型中心誤差 13–15%（原因沒有查），只有 WHAM、HybrIK 與 RTMW3D 較貼（5.5–6.7%）。
- **速度與記憶體**：NLF 最快（16–78 fps，隨解析度與片長變，1080p 影片較慢），InstantHMR 次之（31–48 fps）、HybrIK 22–37 fps；GVHMR 約 3 fps、WHAM 約 6 fps；SAM 3D Body 約 1 fps，最慢（約為 GVHMR 的 1/3、NLF 的 1/16 到 1/78）。
  顯存：InstantHMR 0.4 GB 最少，HybrIK 6.8 GB 最多，全部都在 12 GB 內。
- **跳水（低解析度 456x256、動作極快）所有模型都明顯變差**（in-box 74–92%，jitter 40–250），這是整體現象，不是個別模型；HybrIK 在跳水上抖動特別大（249）。
- **花式滑冰、輪滑的骨盆轉動**：yaw p95 在各網格模型間差不多（約 60–90，RTMW3D 除外），高速旋轉下本來就大。「轉了幾圈、轉向對不對」這類判斷沒有被這些指標量到，要看影片（這也是 finefs 和 SkeletonHub README 對 FlowHMR 的警告所在）。

## 已知問題與限制

- **FlowHMR 沒整合，也沒能重新跑。** 原因：(1) 它是自己的一整條流程（YOLOX 偵測加追蹤、VGGT-Omega 相機、SAM 3D Body 特徵、flow matching 頭），不吃共用框；
  (2) 會轉成 30 fps，輸出是世界座標的 SMPL-H，沒有相機座標，無法和其他模型畫成同一格 2D 疊圖；
  (3) 顯存太大：`scripts/hmr_zoo_flowhmr_probe.py` 在 24 GB 的 TITAN RTX 上，把相機步驟改成每 10 幀跑一次、並設 23.5 GB 上限，仍在 VGGT-Omega 的注意力步驟 OOM（要再要 5.4 GB）。
  依規則（單一模型超過 24 GB 先停下回報）沒有改用 A6000。SkeletonHub 既有的 `detectors/flowhmr_detector.py` 仍然在，但它會把結果寫進 `ReasonMotion_Predictor/baselines/flowhmr/output/`（別的專案資料夾），所以我沒有呼叫它。
  `README.md` 已寫明它在高圈數滑冰跳躍上會失敗。
- **OnlineHMR**：官方沒有 LICENSE；只跑相機座標核心；`LD_LIBRARY_PATH` 要指到 `onlinehmr` 環境的 `lib`。
- **GVHMR 的相機估計**：SimpleVO 在這批影片上有 1/3 失敗，退回靜止相機；數字照樣算，但該片段的相機運動被忽略（對固定機位影片影響不大）。
- **RTMW3D**：見上，3D 欄位不可比，只有 2D 疊圖有意義。
- **HybrIK 的 `service_fast` 與 InstantHMR** 的暫存：HybrIK 每個片段在自己的 clip 資料夾下留一個 `hybrik_raw_*` 暫存資料夾（`smpl.pk`），沒有自動清。
- `env` 的 python 偶爾會出現一次性的「Permission denied」（共用 NFS 的暫時現象，隔幾十秒重跑就好）；`compare.py` 對這個狀況自動重試 3 次。
- `~/.local` 的 numpy 2.x 會蓋過 `skeleton_env` 內建的 numpy（導致 `chumpy` 匯入失敗），所以 `hmr_zoo/run_model.py` 一開頭先把 `~/.local` 放到 `sys.path` 最後面（finefs 腳本的同一招）。
- `detectors/instanthmr_detector.py` 在 SkeletonHub 主資料夾仍是別人尚未提交的檔案；`hmr_zoo/adapters.py` 的 InstantHMR 依賴它（本次沒有碰它，也沒有 commit 它）。
- 追蹤時一次只追一個人（挑出的主角）。畫面有多人且互相遮擋時沒有測。
- 影片是 H.264 轉檔後的版本（剪片段時 crf 17 重新編碼），不是原始位元流，對各模型一視同仁。
