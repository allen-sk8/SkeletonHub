# 從 RGB 影片抓動作：整條流程逐段對照（2026-11-23）

給老師報告用。這份只回答一件事：從一支普通影片抓出 3D 動作，要經過「抓人、2D 骨架、3D 人體」三段，每一段換不同做法，結果差多少。
這是 agent 自己跑的整理，沒有獨立檢查者複核；最後哪個好，請看影片後由人決定。

## 一頁白話結論

1. **抓人這段差異最大，而且最容易被忽略。** 12 支影片裡，只用 YOLO 偵測加「找最近的框」的老做法，在跳水影片 `101b_0001` 整段都框到場邊的人，沒框到跳水選手（抽看的 6 格全錯）；
   用外觀再識別追蹤（會記住選手長什麼樣）的做法則全部框對。另 10 支，兩種做法都框對。抽看的 70 格有選手的畫面裡，YOLO 做法框對 64 格，外觀再識別追蹤框對 70 格。
2. **2D 骨架這段，換模型差異很小，而且沒有一個模型每項都贏。** 以現在的 ViTPose-H 為基準，12 支平均：Sapiens2-0.8B 的 3D 加速度抖動較低（18.85，基準 21.95），但低信心關節較多（8.86%，基準 6.43%）、速度慢 16 倍（1.36 fps，基準 22.21 fps）；
   SDPose-Body 與 RTMW-x 在 2D 抖動上都比基準高（5.77、5.87，基準 5.13）。「3D 對 2D 貼合」四個模型都在 19.3 到 21.4 像素之間。RTMW-x 的信心分數用另一套尺度，不能和其他三個直接比，表中以 2D 抖動與貼合為準。結論是維持 ViTPose-H，換模型沒有看到值得換的差距。
3. **3D 人體這段，OnlineHMR 和 GVHMR 各有取捨。** OnlineHMR 是逐幀即時的（12.8 fps，GVHMR 同一批 3.2 fps，但 GVHMR 要等整段才出結果，兩者算法不同，不是同一種速度）。
   代價是：骨頭長度忽長忽短（骨長變異 9.46%，GVHMR 3.44%）、3D 對 2D 貼合較差（24.7 像素，GVHMR 20.1 像素）、加速度抖動略高（22.93，GVHMR 21.95）。跳水影片差距最大，骨長變異 31.75%，GVHMR 是 4.47%。OnlineHMR 沒有輸出世界座標，所以地面漂移欄無法比。
4. **沒有 3D 真值，所以全文不報「誤差」。** 表中只有：3D 投回 2D 後和 ViTPose-H 的 2D 關節差幾像素、加速度抖動、骨長變異、地面漂移、速度。這些量的是「畫面貼不貼」與「動作穩不穩」，不等於 3D 準不準。

## 流程與基準

基準流程：外觀再識別追蹤框 → ViTPose-H（2D 骨架）→ GVHMR（3D 人體）。一次只換一段，其他段固定，不做全組合。

- 影片：12 支，每個運動 2 支（花式滑冰 `3A_0133`、`4Lz_0018`；輪滑 `v00_3F_0s`、`v25_S_14s`；跳水 `101b_0001`、`107b_0137`；田徑標槍 `javelin_throw_9`、三級跳 `triple_jump_12`；棒球 `pitch_11`、`pitch_21`；打沙包 `sandbag_1`、`sandbag_8`）。
- 3D 欄位的來源：2D 換模型那四列，下游都是 GVHMR，沿用 `outputs/pose2d_zoo/` 現成結果；3D 換模型那兩列，用同一組追蹤框（`hmr_zoo` 的 `padded_112`），OnlineHMR 與 GVHMR 結果也是 `outputs/hmr_zoo/` 現成的，沒有重跑，只在 CPU 上用同一套指標程式（`hmr_zoo.render.compute_metrics`）重算並補上「對 ViTPose-H 2D 的貼合」。
  GVHMR 那列的貼合與抖動，和 `pose2d_zoo` 的 ViTPose-H 列完全一致（20.05、21.95），表示兩邊的算法一致。
- 這次新增的 GPU 工作只有一項：12 支影片的「不含外觀再識別」追蹤（RF-DETR 偵測加 BoT-SORT），neverdie 第 0 張卡，約 2 分鐘，已釋放。

## 第一段：抓人

三種做法：
- **YOLO 做法（紅框）**：YOLO11n 偵測人，取信心最高的當起點，再逐幀找最近的框接起來，沿用 FineFS 現行做法。花式滑冰那 2 支用資料集現成的框；其他 10 支是我們依同一規則重做的，不是資料集原檔。
- **追蹤但不看外觀（黃框）**：RF-DETR 偵測加 BoT-SORT，不用外觀再識別。
- **追蹤加外觀再識別（綠框，基準）**：同上，再加外觀辨識（OSNet），選手離開畫面再回來能接回同一個人。

沒有真值框，判斷方式：每支影片均勻抽 6 格，由我逐格看畫面，判斷框是不是在選手身上；另外算全部幀裡紅框、黃框和綠框的重疊程度（重疊比大於 0.5 的比例）當輔助。綠框是基準，所以這個重疊比只能說「和基準一不一致」，不能說對錯，對錯以抽看為準。

## 第二段：2D 骨架（下游一律 GVHMR，追蹤框用綠框）

直接用 `outputs/pose2d_zoo/summary_by_model.csv` 與各片段 `metrics_2d.csv`，不重跑。以下是 12 支平均，分運動的表在後面的「總表」。

說明：
- 低信心關節：信心分數小於 0.3 的關節比例。RTMW-x 的分數尺度不同（平均 6.9，其他在 0.8 上下），此欄對它沒有意義。
- 2D 抖動：相鄰幀關節移動量占選手身高的比例，越低越穩（但動作本身快時也會高）。
- 左右對調：左右手腳突然互換的次數，平均每支。
- 速度 fps：這一段 2D 模型單獨的速度（neverdie 單卡）。
- 3D 對 2D 貼合：把 GVHMR 的 3D 結果投回畫面，和該 2D 模型的關節差幾像素，越低越貼。因為每列對的是自己的 2D 模型，這一欄在不同模型之間只能當參考。

## 第三段：3D 人體（2D 用 ViTPose-H，追蹤框用綠框）

GVHMR 與 OnlineHMR 在同一批 12 支、同一組框、同一套指標下比較。速度欄來自 `hmr_zoo` 該次紀錄（整個偵測呼叫含前後處理，OnlineHMR 逐幀，GVHMR 整段），不是純網路速度；純網路速度在 neverdie TITAN RTX 上 OnlineHMR 約 23 fps，見 `finefs_preproc/notes/stage2_results.md` 第八節。
OnlineHMR 只輸出相機座標，沒有世界座標，所以「地面漂移」兩欄標 n/a。

## 已驗證與未驗證

已驗證：
- OnlineHMR 在 12 支上的指標，用和 GVHMR 完全相同的程式重算；GVHMR 的重算值與 `pose2d_zoo` 現成 ViTPose-H 結果一致（貼合 20.05、抖動 21.95、骨長 3.44），確認指標程式沒有偏。
- 抓人：70 格抽看，逐格目視。
- 表格 12 支平均與 `summary_by_model.csv` 一致（2D 抖動、貼合、骨長、地面漂移斜率都對得上）。

未驗證或要小心：
1. 沒有 3D 真值，沒有「誤差」；貼合、抖動、骨長都只是自洽性指標。
2. 抓人只有抽看 70 格，且綠框不是人工標註真值；紅框在 10 支是自己重做的（YOLO11n 加最近框規則），結果可能和資料集原檔略有差別。
3. 抓人換了之後，後面 2D、3D 沒有重跑，影響沒有量化。
4. OnlineHMR 只測了相機座標網路，沒有世界座標，沒有比地面漂移；用的焦距是預設假設，貼合較差有一部分可能來自這個假設，沒有分開驗證。OnlineHMR 官方程式沒有授權檔，用於正式流程前要先確認。
5. 只有 12 支、每支約 3 到 8 秒，沒有顯著性檢定；各運動只有 2 支，運動別的差異只當參考。
6. 速度只在 neverdie 的 TITAN RTX 上量，OnlineHMR 與 GVHMR 的速度定義不同（逐幀對整段），不是同一條件。
7. 沒有寫「哪個最好」：每段取捨依用途（要即時、要穩、要貼）而定，請看影片後決定。
